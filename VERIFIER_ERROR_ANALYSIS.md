# DOAR — Verifier Error Analysis (15-image development set, cached data only)

**No live Gemini calls were made.** Every number below comes from already-cached
Observer/Verifier data (`outputs/prototype_cases/development_live_cache/` +
the legacy `gemini_verifier_dev_check_*` dirs) and the real, complete A1/A2
annotations (`annotations/A1/`, `annotations/A2/`). Nothing in the Observer,
Verifier, `reasoning_chain.py`, `RULE_EVIDENCE_MATRIX.csv`,
`CONCERN_DOMAIN_MAP.json`, or any prompt/model/threshold was touched or tuned
to produce this report. Generated by `scripts/verifier_error_analysis.py`;
full candidate-level detail in `VERIFIER_ERROR_ANALYSIS_CANDIDATES.csv`.

> --force-live`) to replace the stale, pre-bbox-fix cached data the case
> study below documents — every bbox is now a valid normalized coordinate.

> **original, accepted analysis** and are left as-is (they remain an

## Method

For every cached Observer candidate on every one of the 15 development images:

- **TRUE** / **FALSE** is decided independently against A1 and against A2,
  using the same deterministic `visual_observer._labels_plausibly_match`
  matcher DOAR uses everywhere else (never an LLM judging agreement) — TRUE
  means the candidate's label matches at least one item that annotator
  recorded.
- The Verifier outcome is its already-computed `verification_status`.
  **"unreviewed" is grouped with "rejected"/"uncertain"** as "removed" —
  `reasoning_chain.py` only ever trusts `case_verification_status ==
  "verified"` entities, so an unreviewed candidate has exactly the same
  downstream effect as an actively rejected one, even though its root cause
  (the Verifier never made a network call at all) is different and is called
  out separately below.
- Four buckets: **(1)** TRUE kept VERIFIED, **(2)** TRUE removed, **(3)**
  FALSE/unmatched removed, **(4)** FALSE/unmatched kept VERIFIED.
- For every bucket-2 (TRUE removed) row, whether it matches a **salient**
  human item, and a **heuristic failure category** — `verifier_visual_miss`
  (the Verifier's own independent read doesn't correspond to anything real
  nearby), `bad_bbox_or_crop_construction` (invalid/out-of-range bbox, a
  too-small crop, or the Verifier's independent read matches a *different*
  real, human-confirmed item — evidence the crop drifted), or
  `no_bbox_never_reviewed`. **This column is a first-pass, evidence-only
  signal, not a final judgment** — the per-case write-ups below are a manual
  reading of each row's actual evidence, which is what "likely failure
  category" in the case studies reflects.

## Case studies

### p2b_0003 — "frowning mouth" / tears

Full 11-candidate trace in the CSV. Six candidates are TRUE-removed against A1:

- **`p2b_0003_c03` "frowning mouth"** (bbox `[0.358, 0.569, 0.187, 0.124]`, area 2.3%, confidence 0.9) → Verifier: `uncertain`, independent label `"unknown"`. A1 matches it as **"downturned mouth" (salient)**. A2 has no matching item recorded for this candidate. **Likely category: verifier visual miss** — a small (2.3% of image area) but not implausibly tiny crop; the Verifier looked and genuinely could not identify it, an honest hedge rather than a confident wrong guess.
- **`p2b_0003_c04`/`c05` "left/right teardrop line"** (areas 0.5%/1.5%) → Verifier: `uncertain`, `"unknown"`. Both match A1's **"tear-like lines" (salient)** and A2's **"Tears" (salient)**. **Likely category: verifier visual miss**, compounded by genuinely tiny crops (<1.5% of image area) that plausibly contain too little visual information for a small independent model to identify.
- **`p2b_0003_c07` "right eyebrow"** (area 0.9%) → Verifier: `uncertain`, `"unknown"`. Matches A1's "eyes" only. **Verifier visual miss** on a very small crop.
- **`p2b_0003_c08` "pink watercolor background aura"** (area **71.6%** of the image) → Verifier: `rejected`, confident (0.95) independent label `"drawing of a sad face"`. Matches both A1's "pink-purple area around head" (salient) and A2's "Background colors" (salient). **Likely category: bad crop construction** — but the opposite failure mode from a too-tight crop: at 71.6% of the frame this bbox is so large it is effectively the whole drawing, so the Verifier reasonably described the *entire picture* instead of the specific background-wash feature the Observer intended, and that description didn't lexically match the Observer's own label.
- **`p2b_0003_c10` "blue ink scribbles"** (area 4.1%) → Verifier: `uncertain`, `"unknown"`. Matches A1's "blue marks" (not salient). **Verifier visual miss.**

**Root cause for p2b_0003 is overwhelmingly "verifier visual miss" on small crops** (5 of 6), plus one large-bbox/whole-image-description miss. Not a label-comparison bug: in every one of these cases the Verifier's own independent read (`"unknown"` or a whole-scene description) genuinely does not correspond to the specific candidate, so the deterministic matcher rejecting/uncertain-ing it is the correct behavior given that input — the problem is upstream, in what the Verifier itself returned.

### p2b_0033 — tears / teddy bear

- **`p2b_0033_c02` "tears"** (area 2.6%) → Verifier: `rejected`, confidence 0.8, independent label **`"mouth"`**. A2 matches it to **"Tears" (salient)**; A1 has no match. **Likely category: bad bbox/crop construction** — `"mouth"` is not a hallucinated concept, it's a real, nearby facial feature; the most consistent explanation is the crop drifted to include the mouth region instead of (or in addition to) the tear marks.
- **`p2b_0033_c04` "teddy bear"** (area 5.0%) → Verifier: `uncertain`, `"unknown"`. Matches A1's **"teddy bear" (salient)**. **Verifier visual miss** — a mid-sized, unambiguous object the Verifier still couldn't independently name.
- **`p2b_0033_c06` "vertical line pattern"** (area **82.4%**, i.e. nearly the whole image) → Verifier: `rejected`, confidence 0.95, independent label `"drawing of a crying boy"`. Matches A1's "background lines / frame" (not salient). **Bad bbox/crop construction** — same whole-image-bbox pattern as p2b_0003_c08.
- **`p2b_0033_c07` "dark side bar"** (area 9.8%) → Verifier: `uncertain`, `"unknown"`. Matches A1's "dark chest detail / object" (not salient). **Verifier visual miss.**

### p2b_0004 — 100% abstention (the "abstention was 1.0" case)

**Root cause identified, not a Verifier-model problem at all: every one of
p2b_0004's 7 cached bboxes is out of the valid [0,1] normalized range**
(heights of 2.7, 3.5, 6.0, 3.68, 3.2, 3.36, 4.14 — i.e. up to 600% of the
image height). `verifier_notes` on every row confirms this directly: *"Bbox
present but a crop could not be produced from this image -- not guessed."*
This is `outputs/prototype_cases/gemini_verifier_dev_check_1786580377`'s
p2b_0004 data specifically, which (per that phase's own prior documentation)
was carried over verbatim from an **older, pre-bbox-schema-fix Observer run**
rather than being regenerated after the fix — every other anchor image in
that same directory *was* regenerated. All 7 candidates end up `unreviewed`;
5 are TRUE against A1 (2 against A2), including salient items ("Clouds",
"Sun", "purple unknown object/shape"). **This is a data-staleness issue, not
a live Verifier-model or label-matching problem** — recommend re-running
p2b_0004 through the current (fixed) Observer, not touching the Verifier.

### p2b_0026 — the largest salient-recall drop in the set (A1: −0.75, A2: −0.60)

Only 3 Observer candidates total, **all 3 removed**, all 3 TRUE and salient
against both annotators:

- `"yellow speech bubble shape"` (area 21.7%, confidence 0.88) → Verifier:
  `rejected`, confidence 0.6, independent label **`"chloroplast"`**. Matches
  A1's "yellow object / shape" and A2's "Yellow oval shape" (both salient).
  This is the single most striking **confident-but-wrong** Verifier read in
  the whole dataset — a plausible-shaped bbox (21.7%, not tiny), a
  mid-confidence but specific wrong guess. **Verifier visual miss.**
- `"white circle eyes/dots"` (area 2.7%) and `"blue horizontal bars"` (area
  4.6%) → Verifier: `uncertain`, `"unknown"` for both, both salient and
  TRUE against both annotators. **Verifier visual miss** on small crops.

p2b_0026 is a simple, sparse line drawing (only 3 candidates total) where the
Verifier failed on all 3 — a strong illustration that low-detail/high-
abstraction drawings are hard for the (smaller) Verifier model specifically.

## Research questions

**A. Is the Verifier actually removing hallucinations?**
Partially. It removes 41.7% (A1) / 35.0% (A2) of FALSE/unmatched candidates
— real signal, not nothing — but the *majority* of false/unmatched
candidates (58.3% / 65.0%) still survive as `verified`. The Verifier is a
weak, not a strong, hallucination filter on this development set.

**B. How many true observations does it remove for every false observation removed?**
**A1: 2.2 true candidates removed per false candidate removed (33/15). A2:
1.29 true candidates removed per false candidate removed (27/21).** Against
both annotators, the Verifier removes *more* true content than false content
in absolute terms (A1) or a comparable amount (A2) — it is not a clean net
gain.

**C. How many salient true observations are lost?**
**21 of 33 (63.6%) A1-salient TRUE-removed candidates, and 22 of 27 (81.5%)
A2-salient TRUE-removed candidates.** The large majority of what the
Verifier incorrectly discards is exactly the content a human found most
noticeable — this is the most concerning finding in this analysis for a
clinical-facing use case, since salient content is disproportionately what a
clinician package would want to surface.

**D. Is the dominant problem the Verifier model itself, bbox/crop construction, or label-comparison logic?**
**Primarily the Verifier model itself** (27 of 39 categorized rows,
`verifier_visual_miss`) — most often an honest `"unknown"` (20/27, small or
visually ambiguous crops the smaller `gemini-3.5-flash-lite` model
genuinely cannot identify), occasionally a confident wrong guess (7/27, e.g.
"chloroplast", "french fries", "avocado" — all on plausible, non-tiny bboxes,
so not a crop-size explanation). **Bbox/crop construction is a real but
secondary and heavily concentrated problem**: `bad_bbox_or_crop_
construction` accounts for 11/39 rows, and the single largest sub-pattern
within it — 6 of those 11 — is entirely p2b_0004's stale, out-of-range bbox
data (one image, one root cause), not a systemic crop-generation bug. The
remaining `bad_bbox_or_crop_construction` cases are two distinct real
patterns: (a) legitimately too-small crops losing context, and (b) bboxes so
*large* (71.6%, 82.4% of the frame) that the crop is effectively the whole
drawing, causing the Verifier to describe the scene rather than the intended
sub-feature. **The deterministic label-comparison logic itself
(`_labels_plausibly_match`) was not found to be a source of error** in any
reviewed case — every rejection/uncertain outcome reviewed here was a
correct comparison result given what the Verifier actually returned; the
comparison function did its job correctly on bad inputs.

**E. Recommendation for the psychiatrist prototype**

Given B and C — the Verifier currently discards more true content than
false, and the majority of what it wrongly discards is salient — **do not
use VERIFIED-only as a hard gate (option 1)** on the current Verifier as
configured; it would hide a large fraction of real, clinically-relevant
content from the psychiatrist with no way to recover it.

**Recommended: option 3, Observer evidence shown with Verifier status as
advisory** (verified / uncertain / rejected displayed as a confidence
annotation on each item, not as a filter), with **option 2's per-status
grouping as the concrete display mechanism** — i.e., 2 and 3 combined rather
than a choice between them: show all Observer-derived content, grouped or
color-coded by Verifier status, so a clinician sees everything a human
annotator would likely have seen while still getting the Verifier's
independent read as a trust signal. `reasoning_chain.py`'s existing hard
gate (`case_verification_status == "verified"` required to satisfy a rule
precondition) should stay as-is for the psychological rule-firing pathway
(that gate exists for a different, still-valid reason — not letting an
unverified detection trigger a clinical rule), but the **raw visual
inventory shown to the clinician** should not be equally strict. This is a
recommendation only; no code was changed to implement it.

## Caveats

- No pixel-level image inspection was performed — `heuristic_failure_
  category` and the case-study categorizations are evidence-based judgment
  calls from label text, bbox geometry, and verifier notes, not ground-truth
  crop review.
- p2b_0004's finding is specific to the cached data `find_saved_
  verification_rows` currently resolves for it (the newest of three
  `gemini_verifier_dev_check_*` directories); it was not re-run live for
  this analysis.
- TRUE/FALSE matching uses the same deterministic matcher as the rest of
  DOAR; a genuine synonym pair with zero shared tokens and no substring
  relationship (e.g. two completely different root words for the same
  concept) would be classified FALSE here even if a human would call it a
  match. No case in this dataset was found where that specific failure mode
  (as opposed to a genuine Verifier miss) explained a false negative, but it
  remains a theoretical gap in the matcher, not something this analysis
  fixed or tuned.
