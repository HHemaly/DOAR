# DOAR V2 feature audit

Machine-readable companion: `artifacts/feature_audit.csv` (75 rows,
generated by `scripts/generate_feature_audit.py` — regenerate it rather
than hand-editing so this document cannot drift from the real code).

**The task's own prompt warned not to trust "~22 features" as exact. It
is not exact: the real count, from actually running
`features.py::objective_feature_row`, is 59**, plus 6 features already
promoted into the canonical evidence layer (`evidence_adapter.py`) and
10 canonical categories that are explicitly declared unimplemented. 75
rows total in the CSV.

## 1. Where features are computed today

| Source | Feature count | Status |
|---|---|---|
| `src/doar/features.py::objective_feature_row` | 59 | Real, deterministic, tested (`tests/test_hog_features.py`-adjacent suites exercise related paths; `features.py` itself is exercised indirectly via `extract.py`/`main.py extract-features`). Two of the 59 (`shape.enclosed_shape_count`, `shape.repetition_score`) are honest `NaN` placeholders — correctly self-reported `missing=True`, never fabricated. |
| `src/doar/evidence_adapter.py::build_evidence_set` | 6 (composition coverage/centroid×3, colour dominant, quality status) | Real, already wrapped in the canonical `EvidenceItem` schema (`evidence_schema.py`), already end-to-end tested (`tests/test_evidence_rule_engine_v2.py`), and now further adapted into this milestone's `FeatureObservation`/`FeatureStore` (`ontology/legacy_adapters.py`). |
| Declared unimplemented (`evidence_adapter.py::UNIMPLEMENTED_FEATURES`) | 10 canonical categories | No extractor exists. Honestly represented as `unavailable` everywhere referenced — never silently omitted, never a fabricated zero. |

`features.py` and `evidence_adapter.py` **overlap** on the underlying
composition measurements (`segmentation.bounding_box_coverage`/
`composition.centroid_x`/`composition.centroid_y` in `features.py` vs.
`composition.bounding_box_coverage`/`composition.centroid_normalized` in
`evidence_adapter.py`) — same numbers, computed once inside
`analysis.py`, exposed twice under slightly different naming
conventions for two different downstream consumers (the classical
feature-model training path vs. the rule-evaluation path). This is not
a bug today (both read from the same `Analysis` object), but it is a
naming-convention duplication worth resolving before a unified feature
ontology fully replaces both call sites — flagged as a `NEXT` item in
`DOAR_V2_MIGRATION.md`, not fixed in this milestone (out of scope, would
touch two tested, live modules for a cosmetic gain).

## 2. Category breakdown (the 59 `features.py` features)

| Category | Count | Deterministic | Full-page visibility required | Interpretation mixed into extraction |
|---|---|---|---|---|
| `quality.*` | 11 | yes | no | no |
| `segmentation.*` | 10 | yes | yes | no |
| `composition.*` (incl. 4 quadrant densities) | 16 | yes | yes | no |
| `colour.*` | 13 | yes | no | no |
| `stroke.*` | 6 | yes | no | no |
| `shape.*` | 3 | yes (2 of 3 are honest NaN stand-ins) | no | no |

**No feature in `features.py` mixes psychological interpretation into
extraction** — every value is a plain numeric/categorical measurement
(ratio, count, density, entropy). This is a genuine strength of the
existing code relative to the architectural risk the task warns against
(`image -> VLM -> psychological conclusion`); interpretation is confined
entirely to `rules.py`/`resources/psychology_sources/rules_registry.json`.

## 4. Reliability concerns worth carrying forward

- Quality-gate thresholds (blur/exposure/noise) are engineering defaults,
  not empirically validated against this dataset (already disclosed in
  `evidence_adapter.py`'s own docstring and `validation_status` field).
- Segmentation is a foreground/background split, not object-aware — it
  cannot distinguish multiple figures from one large figure, which
  silently affects every `composition.*`/`segmentation.*` feature.
- Colour-bin classification is a coarse fixed heuristic, sensitive to
  scanner white balance and paper colour — not perceptual/calibrated
  colour science.
- All of the above are **already disclosed** in the existing code's own
  `limitations`/docstrings; this audit did not discover new hidden
  defects, only consolidated what was already honestly stated across
  multiple modules into one place.

## 5. What this means for V2

Every implemented feature is already interpretation-free at the
extraction layer, which is the single most important precondition for
the target V2 architecture (`image -> observable feature -> ... -> rule
-> evidence profile`, never `image -> conclusion`). The work remaining
is mechanical adaptation (wrapping into `FeatureObservation`, declaring
in `config/feature_ontology.yaml`), not re-engineering.
